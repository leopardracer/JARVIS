# JARVIS architecture

JARVIS is a persistent intelligence layer around a person's financial life. It
captures what the user knows, turns it into a knowledge graph, retrieves the
right context before reasoning, and proposes (never executes on its own)
actions.

```
CAPTURE → REMEMBER → CONNECT → UNDERSTAND → REASON → INSIGHT → ACTION → REMEMBER
```

## Repository layout

```
apps/
  web/                 Next.js app: landing page, product UI, API routes
packages/
  types/               Shared domain types and Zod schemas (no runtime deps)
  db/                  Drizzle schema, database client (Postgres or PGlite), migrations runner, seed
  ai/                  AIProvider + EmbeddingProvider abstractions and implementations
  memory/              Memory service: capture, entity extraction, exact/semantic/hybrid search
  knowledge/           Knowledge graph service: entities, relationships, neighbourhoods, clusters
  broker/              Robinhood Chain read-only helpers now; BrokerProvider, MockBrokerProvider and Robinhood providers in Phase 3
  ui/                  Design tokens and shared React components (shadcn-style)
infrastructure/
  docker/              docker-compose for Postgres + pgvector
  migrations/          SQL migrations generated by drizzle-kit
docs/                  This folder
```

Packages are plain TypeScript consumed from source by the web app
(`transpilePackages`), so there is no separate build step. Dependencies flow one
way:

```
web → memory, knowledge, ai, broker, ui, db, types
memory → knowledge, ai, db, types
knowledge → db, types
broker → types
ai → types
db → types
```

## Runtime

- **Web and API**: Next.js App Router. Route handlers under `apps/web/src/app/api`
  are the only place that touches credentials; nothing secret is sent to the
  browser.
- **Database**: PostgreSQL 16 with `pgvector`. `DATABASE_URL` selects a real
  server (Docker compose provided). Without it, the app uses an embedded
  **PGlite** database (Postgres compiled to WASM, with pgvector) stored in
  `.jarvis-data/`, so the project runs with `npm install && npm run dev` and no
  services. Tests use in-memory PGlite.
- **AI**: selected by `AI_PROVIDER` (`anthropic`, `openai`, `local`, `mock`).
  Embeddings are selected separately by `EMBEDDING_PROVIDER` (`openai`,
  `local`, `hash`). With no keys configured the app runs on the `mock` chat
  provider and the `hash` embedder and says so in the UI.
- **Demo workspace**: "Explore the demo" seeds a private, fictional workspace
  per visitor (rule-based extraction only, so it costs no LLM calls). In Phase 1
  the demo portfolio is seeded directly into the financial tables.
- **Broker** (Phase 3): selected by `BROKER_PROVIDER` (`mock` by default). Only
  documented Robinhood interfaces are used (see `docs/robinhood.md`).

## Request flow: asking JARVIS a question

1. `POST /api/ask` validates the question (Zod) and loads the session user.
2. **Retrieve** (`packages/memory`, `packages/knowledge`):
   - hybrid search over memories: Postgres full-text rank + pgvector cosine
     similarity, merged with reciprocal-rank fusion;
   - entities mentioned in the question are resolved against the graph and
     their 1-hop neighbourhood is added;
   - memories linked to those entities and the most recent theses are added;
   - everything is de-duplicated and trimmed to a token budget.
3. **Reason** (`packages/ai`): the provider receives a system prompt, the
   numbered context (`[M3]`, `[E2]`) and the conversation. It must cite context
   ids and must not invent numbers.
4. **Respond**: the route streams NDJSON events: `sources` first (the exact
   memories and entities used), then `text` deltas, then `done`. The UI shows
   the answer with a "Memory used" panel.
5. **Remember**: the question, answer and cited sources are stored as a
   conversation; an `activity` row records it.

## Capture flow: saving a memory

1. `POST /api/memories` validates input.
2. The memory row is written.
3. Entity extraction runs: a rule-based extractor (known entities, tickers,
   `$CASHTAGS`, `#tags`) always runs; when an LLM provider is configured an
   LLM extractor also proposes entities and typed relationships using
   structured output. Results are merged.
4. Entities are upserted, `memory_entities` links are written and
   `relationships` edges are created with the memory as provenance.
5. The embedding is computed and stored.
6. An `activity` is recorded. Insight detection (Phase 2) listens to these
   activities.

## Safety model

- JARVIS never executes a trade by itself. Every account-changing operation is
  an `action` row that moves through `proposed → approved → executing →
  executed | failed` or `proposed → rejected`. Approval requires an explicit,
  authenticated user request: typing the exact order phrase. Submission is a
  second, separate request; the approved ticket is HMAC-signed and the
  provider refuses anything unsigned, expired or changed after approval.
- Broker credentials are stored encrypted (AES-256-GCM with
  `JARVIS_ENCRYPTION_KEY`) and only decrypted server-side. API responses list
  connections without credentials.
- Demo accounts cannot add live connections, and live actions are never sent
  to the demo brokerage.
- Every financial row carries `data_mode` (`demo` or `live`); the UI labels
  demo data everywhere and live and demo data are never mixed in one view.
- Every sensitive operation writes an `audit_logs` row.
- The model is told that financial figures come only from tools and context,
  and answers are framed as analysis, not personalised investment advice.
